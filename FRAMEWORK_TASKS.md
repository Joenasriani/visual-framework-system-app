# Visual Framework Task Register

This file tracks only work that strengthens the core mission of Visual Framework.

Visual Framework exists to make structured thought visible, inspectable, executable, challengeable, reframable, and reusable.

Every item below must improve at least one of these capabilities:

1. Construct structure
2. Reveal hidden structure
3. Execute explicit reasoning operations
4. Inspect intermediate reasoning outputs
5. Move through abstraction levels
6. Decompose and compose structure
7. Reframe
8. Expose assumptions
9. Preserve alternatives
10. Detect contradiction
11. Represent uncertainty
12. Validate reasoning
13. Attach evidence and provenance
14. Compare structures
15. Navigate recursive frameworks
16. Generate structurally derived insight

# MVP NOW

These are the first reusable executable operations to support because they represent the most useful core reasoning actions while remaining compatible with the current simple Frame runtime.

## 1. DECOMPOSE

Purpose:
Reveal meaningful parts, categories, mechanisms, assumptions, variables, or subquestions inside the input.

Frame order:
Decompose this input into the smallest meaningful structural parts that materially improve understanding. Preserve hierarchy where it exists. Do not split merely for more detail. Return explicit proposed parts and their relationship to the parent.

Why now:
Recursive decomposition is central to the product and works with one input and one output.

## 2. MOVE UP

Purpose:
Find the larger structure, parent category, system, or abstraction level that contains the input.

Frame order:
Move exactly one meaningful abstraction level upward. Identify the most defensible parent structure that contains this input. Explain the containment relationship briefly. If several parents are plausible, preserve them as alternatives rather than forcing one.

Why now:
Upward composition is as important as downward decomposition and distinguishes the product from ordinary mind maps.

## 3. MOVE DOWN

Purpose:
Find the next meaningful lower level beneath the current Frame.

Frame order:
Move exactly one meaningful abstraction level downward. Identify the direct substructures, categories, mechanisms, or instances that belong immediately beneath this input. Do not skip levels unless the intermediate level has no useful structural meaning.

Why now:
It gives the user controlled recursive exploration instead of uncontrolled expansion.

## 4. CHALLENGE ASSUMPTIONS

Purpose:
Expose hidden assumptions and test whether they are necessary, justified, or replaceable.

Frame order:
Identify the assumptions required for this input to hold. Separate explicit assumptions from hidden assumptions. For each important assumption, state the strongest plausible alternative. Do not resolve uncertainty unless the input supports resolution.

Why now:
This turns the graph from a passive structure into an instrument for questioning reasoning.

## 5. REFRAME

Purpose:
Change the structural conditions through which the input is interpreted.

Frame order:
Reframe this input by changing one meaningful structural dimension such as observer, objective, abstraction level, timeframe, causal direction, system boundary, stakeholder, fixed variable, or comparison class. Return the changed frame and what becomes newly visible because of it.

Why now:
Reframing is one of the defining operations of the application.

## 6. FIND MISSING STRUCTURE

Purpose:
Detect important elements that the current representation may have omitted.

Frame order:
Inspect this input for missing structure. Look for omitted causes, stakeholders, assumptions, alternatives, evidence requirements, contradictions, dependencies, variables, consequences, abstraction levels, parent categories, or subcategories. Return only omissions that could materially change understanding.

Why now:
This directly supports discovery and makes AI useful as a structural critic rather than a text generator.

## 7. VALIDATE STRUCTURE

Purpose:
Test whether the represented reasoning is coherent without silently rewriting it.

Frame order:
Validate the structure represented by this input. Identify unsupported claims, category mistakes, hidden assumptions, causal leaps, contradictions, missing dependencies, false certainty, or conclusions that do not follow. Return explicit issues and preserve unresolved questions.

Why now:
The product needs a visible way to challenge its own structures.

# MVP EXECUTION BEHAVIOR

Each operation above should eventually be selectable or reusable as a Frame order.

Each executable Frame must preserve:

1. Input
2. Order
3. Output
4. Execution state
5. Provenance
6. Failure state

A Frame can run independently when its required input is available.

During a Framework Run, the output of a completed Frame becomes available to downstream Frames.

The chain must resolve progressively and visibly Frame by Frame.

The complete Framework must never be collapsed into one hidden global prompt when the visible structure defines separate execution boundaries.
